# 04 · 任务拆解

> 状态：重拆 v2 · 2026-11-26
> 上游：[docs/](README.md)
> **本版目标：让每次 AI 生成都是小 diff、可审查、可回滚。**
> v1 见 git 历史（按模块横切，已废弃）。

---

## 0. 与 v1 的差别（为什么重拆）

v1 的切片是**按模块**切的：`ACP 拉起` → `ACP 会话` → `持久化`。结果每个 Issue 做完**演示不了任何东西**，
且模块之间的接口在拆解时并不存在，只能靠猜。

v2 改成**按用户路径**切：每一刀都对应「人打开界面能看到的一个变化」。
代价是同一个模块会被多次触碰（如 worktree 在 M2 出现 3 次），但换来三个好处：

1. **每刀都能演示**——验收标准写的是「用户看到什么」，不是「模块具备什么能力」。
2. **每刀的 diff 天然小**——只为一个可见结果服务，不会顺手把整层写完。
3. **可回滚**——任一 PR 回滚，最多损失一个可见能力，不会留下半套架构。

## 1. 小 diff 的硬性预算

| 项 | 上限 | 超了怎么办 |
|---|---|---|
| **`src/` 变更行数** | **≤ 1000 行**（新增+删除，含注释/docstring） | 超 1000 当场拆 |
| **`src/` 触及文件数** | **≤ 12 个** | 继续拆 |
| 单个 Issue 工作量 | **≤ 4 小时** | 继续拆 |
| 单个 PR 新增公开接口 | **≤ 3 个方法** | 拆成「先能用假的，再换真的」 |

> 这是**写作时的约束**，不是事后检查。如果拆到发现某个 Issue 必然超预算，说明它不是一个切片，是两件。
>
> 每一刀交付前还要过一份清单：[09-slice-dod.md](09-slice-dod.md)（规格、边界矩阵、反向注入、
> PR 体必填项、独立审计）。预算管**大小**，DoD 管**质量**，两者不互相替代。

### 1.1 计量口径：行数与文件数**只统计 `src/`**

**裁决（S4 收尾，2026-11-26）**：`tests/`、`tools/acceptance/`、`docs/` **不计入行数 / 文件数上限**。

| 目录 | 计入上限 | 理由 |
|---|---|---|
| `src/` | ✅ | 产品体积与长期维护面就在这里 |
| `tests/` | ❌ | 验收成本，不是产品体积；每多一条验收标准就该多一条测试 |
| `tools/acceptance/` | ❌ | 同上（真实浏览器验收，不进 CI、不进依赖） |
| `docs/`（含 codemap） | ❌ | 设计/代码地图是维护资产；门禁已经强制「改 `src/` 必须同步 codemap」 |

**为什么改**：S1/S2/S3/S3.5/S4 五刀全部「超标」，但 S4 拆开看是
`src/` **6 文件 / +397 行**（**在限内**）、其余 19 文件是测试 633 行 + 验收脚本 480 行 + 文档 599 行。
上限本身没错，是**分母**错了：按旧口径，守规矩的唯一办法是删测试或砍验收项——那只是把超支藏起来，
而不是变小。`src/` 的行数上限仍然是硬约束，超了照样继续拆。

**新增约束**（把「不计入」换成可检查的）：不计入上限 ≠ 不设防——测试与文档靠
DoD 与门禁守：**每条验收标准至少一条真测试**、**改 `src/` 必须同步 `docs/codemap/`**（已有门禁）。

> 历史 Issue 文档里的「≤400 行 / ≤12 文件」交付检查项按**当时**口径书写，不回改；
> 从 S4 起的切片按本节口径结算。

### 1.2 上限的两次标定（400 → 700 → 1000）

尺子改过两次，两次都用同一套方法：拿**已交付切片**的实测数字回算，把「旧数字为什么会低估」
写清楚，而不是对某一次超支就地解释。历史记录不回改。

#### 1.2.1 第一次标定：400 → 700（S6 收尾，2026-11-27）

S6 交付时逐刀回算了 `src/` 实际增删行（`git diff --numstat <merge>^1 <merge> -- src/`）：

| 切片 | `src/` 增删行 | 其中 `web/assets.py` | 当时上限 |
|---|---|---|---|
| S1 | 492 | 48 | 400 |
| S2 | 663 | 269 | 400 |
| S3 | 978 | 202 | 400 |
| S3.5 | 134 | 0 | 400 |
| S4 | 421 | 226 | 400 |
| S5 | 641 | 273 | 400 |
| S6 | 687 | 278 | 400 |

**七刀里六刀超 400**——除 S3.5 外，上限从未被遵守过。那不是「大家不守规矩」，是**数字标错了**：
每刀都在「接受例外、如实报」，等于没有预算（规则要么被遵守、要么被改到可遵守）。

两个结构性事实决定了这个量级：

1. **含页面的刀天然 +200~280 行**：没有前端构建链（S1 的裁决），一个面板的 DOM + CSS + JS
   全内联在 `web/assets.py` 一个字符串里（S2 269 / S3 202 / S4 226 / S5 273 / S6 278）。
2. **注释密度是刻意的**：本项目多次因"注释写了没跑过的推断"退回（T33/S4），所以要求把
   「为什么这么写、踩过什么坑」写进代码；按逻辑行估会系统性低估 50%~70%（S5 的 E2 教训）。

所以**当时**的上限改成 **700 行**：它覆盖七刀里的六刀，**唯一仍超的是 S3（978）**——而 S3 恰好也是
审核退回最多的一刀（T25/T29/T31 全出自它）。上限的意义是**预警**，不是记账；真正的防波堤是
下面三条（都不变）：**一个 PR 只做一个用户路径**、**新增公开接口 ≤3 个方法**、**`src/` 文件数 ≤12**。
超过上限就在**规格阶段**拆，不是做完再解释（当时的数字是 700）。

> 这条不改变历史记录：S1–S6 的 Issue/PR 里写的「超 400」都是真的，只是当时的尺子错了。

#### 1.2.2 第二次标定：700 → 1000（S7 之后，2026-11-27）

S7（M2 第一刀）交付后回算：`git diff --numstat e744ea3^1 e744ea3 -- src` → **945 行 / 9 文件**
（+908 / −37），其中 `web/assets.py` 231 行。规格阶段估的是 507（[S7 §6](issues/S7-worktree-visible.md)），
差 1.9×；**700 这个数字没有覆盖它**，而估 507 是在写代码之前做的——所以这不是「事后解释超支」，
是估算方法对这类切片系统性低估。

700 为什么不够，三个可核对的事实：

| 事实 | 证据 |
|---|---|
| S7 是**内核第一次写用户仓库**的一刀：多了两个新模块（写面 `gitops/worktrees.py` 226 + 编排 `api/worktrees.py` 300，共 526 行），旧切片没有这一类 | S7 §12.4 的逐文件表 |
| 含页面的刀天然 +200~280 行（工作区卡片 231），与 S6 的 278 同量级 | 上面那条 numstat |
| 结构性防波堤全部满足：一个用户路径（分配→可见→回收）、新增公开方法恰好 3 个、`src/` 9 ≤ 12 文件 | S7 §1 / §12.4 |

**新上限：`src/` ≤ 1000 行 / ≤ 12 文件。** 和第一次一样，这是「预警线」，不是记账；真正的防波堤
仍是那三条。**反向约束（新增）**：如果连续两刀都逼近或超过 1000，说明**切片方式**错了（不是尺子
又错了）——应当回到 §0 的切法（按用户路径再切一刀），而不是第三次改数字。M2 收尾时按同样方法
回算 S7–S14，再决定 1000 是留、是调、还是拆法要改。

> 历史记录不变：S1–S6 的「超 400」与 S7 的「超 700」都是真的；变的是尺子和拆法，不是当时的事实。

## 5. 优先级

- **P0**：S1~S5、S7~S11 —— 端到端最小闭环，缺一刀就演示不了「派活 → 出 diff」。
- **P1**：S6、S12~S14 —— 让闭环**可被人验收**（有收件箱、能批准）。
- **P2**：S15~S20 —— 可上线性。其中 **S16（越权拦截）优先级高于其他 P2**：拦不住就不该上线。

## 6. 全局禁止事项（适用所有 Issue）

- **不得**把 `.env` 或凭据写入代码、测试、日志、提交。
- **不得**在提交前跳过 `bash scripts/check.sh`。
- **不得**在通用接入层写单个 Agent 的特例分支（如 `if agent == "opencode"`）。
- **不得**把能力旗标硬编码；能力必须来自运行时响应。
- **不得**让 Bot 拥有合并（L4）能力。
- **不得**在未实测前，在文档或 UI 中宣称某能力「已支持」。
- **不得**修改 `~/.dsh/profiles/` 或用户现有环境配置。
- **不得**用 mock 替代 git / ACP 的真实行为作为唯一测试手段。
- **不得**在单个 PR 里同时改动两个用户路径（超预算，见 §1）。
- **不得**直推 `main`；一律特性分支 + PR。
